# 공격 구현 충실도와 연구 방향 점검

2026년 10월 8일 기준 정적 코드 감사이다. main의 `c2b1399`와 평가 브랜치의 `9d91222`를 확인했다. 원본은 FUBA `bc233610aca36e1647d0c815597cc7148292139d`, BadFU `0a2117feab58faf5b7e2a1e5e1759112087d6049`로 고정했다. 비교 결과 목록은 [감사 기록 JSON](ATTACK_FIDELITY_2026-10-08.json)에 있다. 데이터셋·체크포인트가 없으므로 원 실험의 학습과 입력 이미지 동일성까지 검증한 것은 아니다.

FUBA는 원 공격 핵심 구현을 보존한 소규모 실행이다. BadFU 탐지 실험은 공개 코드의 여러 경로 중 공격자와 위장 클라이언트를 분리한 경로를 축약한 것이다. 따라서 두 공격의 모든 논문 설정을 그대로 재현했다고 표현할 수 없다. 특히 평가 브랜치의 실제 FU 결과에는 데이터 분할과 산출물 대응을 먼저 확인해야 하는 문제가 있다.

### 실제 FU 평가의 우선 확인 사항

**데이터 분할 불일치.** `exp/evaluation`의 학습은 `config.seed`로 데이터 분할을 하지만, `unlearn_method/retrain.py`는 `torch.manual_seed(522)`로 다시 분할한다. `unlearn.py`와 `run_full_experiment.sh`에는 학습 seed를 전달하여 같은 분할을 복원하는 연결이 없다. seed 1로 학습한 실험을 이 경로로 재학습하면 client 4가 동일한 샘플 집합을 뜻하지 않는다. 클라이언트 ID만 맞춰서는 같은 삭제 요청의 retrain 기준선이 되지 않는다. main의 기존 학습·retrain은 둘 다 522를 사용하며, 이 문제는 seed 확장 후의 연결에서 특히 발생한다.

**이전 산출물 재사용 가능성.** `run_full_experiment.sh`는 `saved_models/global_<FU>_iba_mnist.pkl`이 이미 있으면 현재 실행의 체크포인트를 복사하지 않는다. 이 경로에는 실행 이름이나 seed가 없다. 기존 파일이 남아 있으면 다른 실행의 FU 모델을 평가할 수 있다. 저장된 JSON만으로 과거 결과가 실제로 오염됐다고 확정할 수는 없지만, 파일 해시와 실행 ID를 확인하기 전에는 대응을 보장할 수 없다.

**트리거와 좌표계.** 원 retrain은 새 모델과 IBA 생성기를 학습한다. 반면 `purify_unlearned.py`는 원 공격 궤적에서 얻은 V와 원 공격의 최종 생성기로 FU 모델을 평가한다. 원 트리거에 대한 지속성 평가와 새 공격 생성기에 대한 ASR을 구분하고, 새로 초기화된 모델에 과거 파라미터 부분공간을 적용하는 타당성도 검증해야 한다. 이것이 낮은 정화 효과의 원인이라고 현재 확정할 수는 없다.

따라서 앞서 정리한 ASR 63.70→60.20%는 **현재 로그의 관측값**이다. 동일 삭제 대상·동일 실행 산출물 조건을 확인하기 전에는 방법의 최종 성능이나 실패 원인을 확정하는 근거로 쓰지 않는다.

[저자 저장소 기준 커밋](https://github.com/BingguangLu/BadFU/tree/0a2117feab58faf5b7e2a1e5e1759112087d6049)의 대상 파일 208개 중 `BadFU_src/BadFU-main`에는 200개가 동일하고, `bd_dataset_v2.py`에 역직렬화·deepcopy 재귀 방지 변경이 있다. DBD 방어 유틸리티의 `data/` 소스 7개는 없다. 이는 현재 BadNet 경로에서 확인한 공격 변형과는 구분되는 저장소 완전성 문제다. 상위 `BadFU_src`에는 원본 파일 일부만 있으므로 완전한 독립 사본으로 간주하지 않는다.

`badfu.py` 자체와 전처리 원본은 저자 코드와 일치한다. 다만 우리가 관측한 탐지는 추가 파일 `fl_detect_badfu.py`와 `unlearn_from_traj.py`를 사용한다.

|---|---|---|
| 공격 배치 | 원본 `ul` 경로와 같이 client 0에 clean+백도어, client 5에 같은 clean+위장 데이터를 배치 | 공개 코드의 특정 분리 설정을 따른 것 |

[BadFU 논문](https://arxiv.org/html/2508.15541v1#S4)은 단일 악성 클라이언트와 샘플 삭제를 다루며, [방법 절](https://arxiv.org/html/2508.15541v1#S5.S3)은 트리거를 붙이고 원 레이블을 유지하는 위장 생성 방식을 설명한다. 반면 공개 전처리는 UBA-Inf 단계와 `cv_pert` 입력을 포함한다. 공개 코드의 특정 실행 경로를 따랐다는 것과 논문의 모든 가정을 동일하게 재현했다는 것은 별도 주장이다.

### 클라이언트 수 재확인과 해석 정정

논문 arXiv v1의 IV-A는 단일 악성 클라이언트를 명시하고, Algorithm 1은 같은 로컬 데이터에 D_bd와 D_c를 모두 합친다. 반면 저자 공개 코드의 `ul` 실행 경로는 실제로 두 클라이언트를 분리한다. `badfu.py` 167–168행은 client 0에 clean+백도어를 넣고, clean+위장을 갖는 client 5를 추가한다. 433–450행은 여섯 클라이언트를 각각 로컬 학습한 뒤 집계한다. 441–442행은 이후 보정에 사용할 기록에서 client 5를 제외하고, 514–526행은 백도어가 남은 다섯 클라이언트로 언러닝 보정을 수행한다. 이는 한 클라이언트 내부의 임시 데이터 분할만을 뜻하지 않는다.

따라서 현재 두 클라이언트 탐지 설정은 우리가 임의로 만든 가정이 아니라 **공식 공개 구현의 언러닝 경로에 근거한 설정**이다. 단일 클라이언트라는 본문 서술만으로 현재 쌍 탐지 연구의 타당성을 부정해서는 안 된다. 다만 본문과 이 실행 경로 사이의 차이는 명시해야 하며, 코드만으로 논문의 모든 결과표가 이 경로에서 생성됐다고 확정하지 않는다. 근거: [논문 IV-A](https://arxiv.org/html/2508.15541v1#S4.S1), [공식 데이터 배치](https://github.com/BingguangLu/BadFU/blob/0a2117feab58faf5b7e2a1e5e1759112087d6049/badfu.py#L159-L188), [개별 학습과 집계](https://github.com/BingguangLu/BadFU/blob/0a2117feab58faf5b7e2a1e5e1759112087d6049/badfu.py#L427-L452).

백도어와 위장 업데이트가 서로 다른 클라이언트에 보이는 분리 설정은 쌍 통계에 유리할 수 있다. 같은 clean 데이터를 공유하는 구조도 통계에 영향을 준다. 단일 클라이언트 안에서 상쇄가 일어나면 클라이언트 간 반대 방향 쌍은 보장되지 않지만, 이는 현재 공식 분리형 경로의 실험을 무효화하는 근거가 아니라 적용 범위와 추가 평가의 문제다.

근거: [원 BadFU 구성](../../BadFU_src/BadFU-main/badfu.py), [탐지 runner](../../BadFU_src/BadFU-main/fl_detect_badfu.py), [전처리 wrapper](../../BadFU_src/BadFU-main/regen_and_detect.sh).

### 최종 실험 조건 재확인

확인 범위는 arXiv v1의 IV–VII절과 위에 고정한 저자 저장소 커밋이다. IEEE 출판본 DOI는 이번 조회에서 열리지 않아 출판본의 수정 여부까지 확인했다고 주장하지 않는다. README는 이 저장소를 CIFAR-10/ResNet18 예제 실행으로 설명하므로, 전체 논문 표의 재현 패키지로 간주하지 않는다.

| 항목 | 논문 서술 | 공개 예제 코드에서 확인한 실행 |
|---|---|---|
| 클라이언트 | 기본 K=5, 악성 클라이언트 1명 | clean/bd/cv 경로는 5명, 공격 활성화용 ul 경로는 추가 client 5를 포함해 6명 |
| 한 클라이언트에 D_bd+D_c 배치 | Algorithm 1의 설정 | cv 경로에 존재. 이후 538–561행은 정상 client 1을 제거하며 D_c를 유지함 |
| 위장 제거에 의한 활성화 | D_c의 영향 삭제 | ul 경로에서 위장 client 5를 제외. 단일 client 내부 D_c만 삭제하는 실행과 다름 |
| 로컬 학습 | SGD 0.01, FedAvg 5 epochs, batch 32 | SGD 0.01, 5 epochs. 학습 DataLoader는 batch 64이며 상단 batch_size=32는 평가 로더에 사용 |
| FL 및 데이터 | FedAvg/FedSGD/FedProx, Dominant Class/Dirichlet | 예제는 데이터 수 가중 FedAvg, Dominant Class 0.7, 전원 참여, 40 rounds |
| 반복 | 서로 다른 seed로 3회 평균 | badfu.py에 seed=42로 단일 실행 지정 |
| 공격 입력 | CIFAR-10 백도어 850개, 위장은 동일 트리거·원래 레이블 | 준비 명령은 pratio=cratio=0.017, target=0. UBA-Inf 호출 및 파일 이동을 포함하므로 최종 이미지 동일성은 산출물로 확인 필요 |

특히 **cv 경로의 존재만으로 단일 클라이언트 내부의 위장 데이터 삭제에 의한 활성화가 이 공개 예제에서 검증됐다고 주장할 수 없다.** cv 경로의 후속 보정은 정상 클라이언트 삭제 실험이다. 공개 예제에서 위장 제거로 활성화하는 FU 경로는 분리형이며, 이것이 현재 쌍 탐지의 직접적인 평가 근거다. 논문의 결과표와 각 코드 경로의 실행 산출물 연결은 제공된 코드만으로 확정하지 않는다.

우리 탐지 runner는 이 분리형 데이터 배치를 따른다. 다만 기본 15라운드(기존 보고 12라운드), 전처리 마지막 파일 조작 생략, 학습·FU 별도 구현이 있으므로 원 논문 수치의 완전 재현과는 구분한다. 이번 확인은 소스 감사이며 새 학습 실행이나 수치 재현이 아니다.

## 연구 방향의 명확한 범위

목표는 **별도의 가상 언러닝 시뮬레이션 없이, 요청된 실제 언러닝을 이행하면서 정화를 수행하는 것**이다. 시뮬레이션 횟수를 줄이거나 탐지 실패 시 시뮬레이션으로 전환하는 것이 제안의 핵심은 아니다. 탐지·정화에 따른 추가 연산은 측정하되, 실제 삭제 이행에 필요한 FU 계산과 위험 판정용 가상 FU를 구분한다. 삭제를 거부하지 않는 것은 연구의 설계 제약으로 둔다. 특정 법률의 적용 범위나 기여 차감만으로 권리가 보장된다는 주장은 포함하지 않는다.

우선 FUBA와 BadFU 공식 코드의 클라이언트 분리 공격을 재현하여 쌍 탐지를 평가한다. BadFU 본문의 단일 클라이언트 데이터 삭제 설정은 별도 확장·한계 평가로 구분한다. 분리형 설정에서 얻은 결과를 BadFU의 모든 설정에 일반화하지 않는다.

### 쌍 검사를 줄이는 방법

전체 쌍 O(n²) 검사를 기준선으로 유지한다. 삭제 요청 시 요청자 q는 이미 알려져 있으므로 우선 q와 나머지 n−1명만 비교하는 변형을 검증한다. 이는 요청자와 타 클라이언트 간 상쇄가 관측되는 설정을 전제로 한다. 클래스 수 C, 헤드 차원 d, 누적 라운드 R을 포함하면 비용도 O(n·C·d·R)로 기록한다.

다음으로 저차원 요약·클래스별 집계로 후보를 줄인 뒤 후보 쌍에서 정밀 통계를 계산한다. 후보 누락률과 데이터 분포 변화에 대한 영향을 함께 측정한다. 준비 단계 전체 비용·저장량·요청당 추가 비용을 분리하고, 여러 삭제 요청에서 비용이 어떻게 분산되는지도 보고한다.

비교 대상은 추가 위험 판정을 위해 언러닝을 여러 번 시뮬레이션하는 방식이다. 우리 방식도 실제 삭제를 위한 FU는 한 번 수행해야 하므로, 공통 FU 비용을 빼고 추가 검사·정화 비용끼리 비교한다. 동등한 탐지 재현율 또는 동등한 정상 피해 조건에서 비용 차이를 제시한다.

### 탐지 불확실성과 정화 강도

검출기의 전체 정확도나 raw O 점수를 개별 요청의 악성 확률로 쓰지 않는다. 별도의 정상·공격 검증 실행에서 신뢰도를 보정하고, 타깃·군집·방향 추정의 불확실성을 구분한다. 신규 공격·분포 이동에서는 보정도 깨질 수 있으므로 확률 해석의 범위를 명시한다.

정화 강도 λ, 제거 랭크 k, 적용 층을 변화시켜 정상 성능 손실과 잔여 공격 위험의 관계를 측정한다. 탐지 실패·오탐 시에도 요청된 삭제 대상은 q 또는 지정 샘플 집합으로 고정한다. 현재 `pipeline_detect_purify.py`는 `req_hat`을 실제 차감 대상으로 사용하므로, 서비스형 평가에서는 요청자 추정과 삭제 대상 결정을 분리해야 한다.

평가 시 공격자 정답으로 만든 V와 탐지로 만든 V를 둘 다 사용해 정화 자체의 한계와 탐지 오차를 분리한다. 정답 집합은 오라클 기준선에서만 사용한다. 실전 방어의 λ를 정할 때 테스트 ASR이나 실제 공격 트리거를 몰래 사용하지 않는다. 서버의 깨끗한 검증 데이터·의심 신호를 쓰려면 해당 접근 권한을 명시한다.

### 위장 데이터와 삭제 제약

사용자가 말한 C는 위장 데이터 D_c이다. D_c가 삭제 요청의 대상이면 “강한 공격일 때 D_c 일부를 남겨 상쇄”하는 정책은 삭제 이행을 요구하는 설계와 충돌한다. 강한 정화는 삭제 후 남은 모델·잔존 기여·허용된 검증 데이터에 적용하는 것으로 정의하는 것이 일관된다. D_c 원본 또는 그 정보를 사용하는 경우에는 접근 가능성과 삭제 후 정보 보존 범위를 명시하고, 망각 성능을 별도로 검증해야 한다.

### ASR 10에서 15퍼센트 이후 FL 지속 가설

10~15%는 이번 연구의 후보 목표 구간이며 보편적인 안전 기준은 아니다. 깨끗한 기준 모델의 동일 트리거 ASR, 적용 분야의 피해, 정상 정확도를 함께 보고한다. 공격 트리거를 모르는 운영 환경에서 ASR을 직접 읽어 임계값까지 정화를 조절할 수 있다고 가정하지 않는다.

정화 직후의 ASR보다 **그 이후의 궤적**이 핵심이다. 같은 정화 모델에서 다음 세 조건으로 후속 FL을 진행한다.

| 조건 | 검증할 질문 |
|---|---|
| 남은 참여자가 정상 데이터로만 학습 | 잔여 백도어가 자연 감소하는가, 유지되거나 되살아나는가 |
| 공격자가 백도어 주입을 계속함 | 일회 정화가 지속 공격에 얼마나 버티는가 |
| 공격자가 잠복 후 재참여함 | 부분 참여·재참여 시 다시 활성화되는가 |

정화 없음, 통째 제거, 일회 V 정화, 매 라운드 또는 위험 상승 시 재정화, 허용된 깨끗한 데이터만으로 보정하는 방법을 비교한다. ASR의 마지막 값뿐 아니라 후속 구간 최대값·곡선 면적·목표 구간 이탈 빈도와 ACC·비용·망각 지표를 보고한다. 정상 FL이 ASR을 낮춘다고 전제하지 않는다.

## 실행 우선순위

1. FU에서 학습 당시 데이터 분할을 복원하고, 실행별 산출물·해시·seed를 고정한다. 원 트리거와 retrain 트리거 평가를 구분한다.
2. FUBA와 BadFU 공식 코드의 분리형 실행 경로를 우선 재현한다. BadFU 본문과 구현의 차이를 명시하고, 단일 클라이언트 위장 샘플 삭제 설정은 적용 범위를 검증하는 별도 평가로 둔다.
3. 실제 삭제 대상 고정, 정상 실행의 공격 유무 판단, 전체 쌍 대비 요청자 중심 검사의 누락률을 검증한다.
4. 실제 FU 모델에서 오라클·추정 V를 비교하고 정화 강도·랭크·적용 층과 탐지 오류를 함께 변화시킨다.
5. 유효한 정화가 확보되면 후속 FL 세 조건을 독립 seed들에서 평가하고, 추가 시뮬레이션과 동등 조건의 비용 비교를 수행한다.

이번 감사에서는 원 실험 코드를 수정하거나 재학습하지 않았다. 발견된 결과 대응 문제를 해결하기 전에 기존 로그를 논문 최종 수치로 확정하지 않는다.
