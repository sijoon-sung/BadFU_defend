# 헤지 파일럿 — "위장자와 운반자의 갱신은 반대 방향인가" (브랜치 `exp/hedge-pilot`)

## 1. 무엇을 확인하려는가
제안: 위장형 백도어는 금융의 헤지와 같다. 운반자(백도어를 심는 쪽)와 위장자(눌러서 숨기는 쪽)의 갱신이 서로 반대라서 합(순노출)만 보는 FedAvg 에는 안 보이지만, 갱신 하나하나의 크기 합(총노출)과 쌍의 반상관을 보면 드러난다. 그러면 **서버가 이미 받은 갱신만으로, 학습·데이터·트리거·시뮬레이션 없이** 짝을 찾을 수 있다.

가정이 맞으려면: 위장자–운반자 쌍의 라운드별 코사인이 다른 쌍(위장자–정상, 운반자–정상, 정상–정상)보다 뚜렷이 낮아야 한다. 특히 non-IID(Dirichlet α=0.5)에서 정상 쌍끼리 자연히 생기는 반상관과 갈려야 한다.

## 2. 무엇을 재나 (`FUBA/analysis_hedge.py`)
저장된 라운드별 갱신 u_j^t = (로컬 − 직전 전역)/K 로:
1. 쌍 코사인 cos(u_i^t, u_j^t) — 전체 매개변수 / 층별(conv1, conv2, fc1, fc2, fc3) / 그 라운드의 평균 갱신을 뺀 뒤. 쌍마다 라운드 평균.
2. 총노출 Σ‖u_j‖ 와 순노출 ‖Σu_j‖, 비율, 클라이언트별 총노출 몫.
3. 클라이언트마다 "가장 반대인 상대" (라운드별).
4. 누적 기여 U_j 끼리의 코사인 (요청이 오기 전에 계산해 둘 수 있는 판).

판정 (`FUBA/aggregate_hedge.py`): 위장자–운반자 쌍 vs 나머지 쌍을 "코사인이 낮을수록 양성"으로 가르는 AUROC. 0.5 = 구분 못 함, 0.9 이상 = 뚜렷. 네 판(전체/중심화/층별/누적) 모두 계산.

## 4. 지금까지의 결과 (로컬, IID, K=8, 1 시드 — `FUBA/logs/analysis/hedge_loc_fuba.json`)
| 판 | 위장자–운반자 | 위장자–정상 | 운반자–운반자 | 정상–정상 | 운반자–정상 |
|---|---|---|---|---|---|
| 전체 매개변수 | +0.56 | +0.60 | +0.73 | +0.65 | +0.45 |
| 층별 | 전부 양수 (+0.47 ~ +0.71) | 전부 양수 (+0.54 ~ +0.85) | | | |
| 공통 성분 제거 | −0.44 | −0.50 | +0.23 | +0.44 | +0.02 |
- 위장자의 갱신은 운반자의 반대가 아니다. 정상과 똑같이 같은 방향이다.
- 공통 성분을 빼면 위장자는 모두와 반대가 된다 (제일 큰 갱신이라 평균 반대편에 혼자 선다). 짝이 아니다.
- 총노출/순노출은 라운드가 갈수록 1.04 → 1.45. 위장자가 총노출의 32 % (정상 8 %). 이것은 크기 신호이고 non-IID 소유자도 같은 신호를 낸다.
- 판정 점수 (`aggregate_hedge.py`): 전체 매개변수 AUROC 0.33, 중심화 0.83 이지만 짝 특이도(위장자–운반자 vs 위장자–정상) 0.00 → 점수 0.33 → **갈리지 않음**. 즉 중심화 판의 0.83 은 "위장자가 모두와 반대"일 뿐이다.
- 해석: FUBA 의 위장자 벡터는 "운반자 갱신의 음수"가 아니라 "공격 모델에서 정상 데이터로 미세조정한 차이"다. 트리거 입력에서만 반대로 작용한다. 그래서 매개변수 공간에서는 반상관이 없고, 짝은 **위장자를 뺀 뒤 깨어난 입력 위에서** 재야 보인다 (dev 의 `cancel_fu.py` 회전 2: 운반자 −0.9, 정상 +0.7).

## 5. 판정 규칙 (돌리기 전에 정해 둔다)
- dir05 와 iid 에서 전체 매개변수 판 AUROC ≥ 0.9 → 가정 성립. 이 방향으로 진행 (저장 갱신만 쓰는 탐지).
- 0.7–0.9 → 약함. 층별·중심화 판에서 어느 하나가 ≥ 0.9 이고 위장자–정상 값이 운반자 값과 다를 때만 진행.
- < 0.7 (로컬 결과가 이렇다) → 가정 기각. 짝 찾기는 활성화 입력 위에서 (dev 의 TRACE) 로 간다. 헤지는 서론의 비유로만.

## 6. 제안의 나머지 부분에 대해
- "클라이언트 단위 언러닝을 강제하면 BadFU 가 원천 봉쇄된다": 백도어 샘플과 위장 샘플이 **한 클라이언트** 안에 있는 논문 설정에만 해당. 공개 코드 설정(두 클라이언트)과 FUBA 에는 효과가 없고, 공격자는 두 클라이언트로 나누면 된다. 정책이지 탐지가 아니다.
- "요청이 오기 전에 위험을 미리 안다": 4 번 판(누적 기여 코사인)이 그것인데, 위 결과대로 짝이 안 보인다.
- "진짜 공격자를 지목한다": dev 의 TRACE 가 하는 일. 저장 갱신만으로는 안 되고 빼 본 뒤에 된다.
