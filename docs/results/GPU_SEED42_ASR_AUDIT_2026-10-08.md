# GPU seed 42: ASR 100% 원인 점검

2026-10-08 · 결과 업로드 커밋 `2fc5327` 기준. 원본 결과는 수정하지 않았다.

**현재 근거는 ASR 계산식 오류보다 탐지 신호의 실패와 제한된 정화 방법의 실패를 가리킨다.** 코드 검증과 로그 분석은 수행했지만, 이 장비에는 원 실행의 모델·history·이미지와 CUDA가 없어 GPU 모델을 직접 다시 추론하지는 못했다. 코드 점검만으로 모든 데이터 문제를 배제할 수는 없다.

## 1. detected는 탐지 단계에서 정화가 꺼졌다

- 요청 점수 `0.9277817011`, 임계값 `1.0541042089`: `no_alarm`.
- 후보 `pairs=[]`, 기저 rank 0, 모든 gamma 0, 실제 정화량 0.
- none / zero / detected의 최종 모델 SHA-256이 동일하다.
- 실제 백도어 클라이언트 0과 요청자 5 사이의 최종 클래스별 점수는 **10개 모두 0**이다. 공동 관측은 16회이므로 관측 부족 처리 때문은 아니다.
- 최대 점수는 정상 클라이언트 4의 클래스 1에서 나온다. 실제 공격 타깃은 클래스 0이다.
- 같은 seed의 정상 대조군 요청 점수는 `0.9682745337`로 공격 실행보다 높다.

따라서 요청 임계값을 단순히 낮춰도 실제 공격자를 찾았다고 할 수 없다. 현재 점수는 반대 방향·상쇄량·크기·시간적 반복성을 곱한다. 최종 점수 0만으로 raw cosine이 항상 양수였다고 단정할 수는 없다. raw 점수와 반복성 조건을 확인하려면 `history.pt`가 필요하다.

가능한 설명은 정상 기여가 공격 관련 성분을 가리는 것이다. 이 실행에서 클라이언트 0과 5는 정상 이미지 9,478개를 공유하고, 각각 백도어/위장 이미지 850개를 추가한다. 두 전체 헤드 업데이트가 반드시 반대라는 가정은 성립하지 않을 수 있다. **이는 아직 원인 가설이며**, 저장된 업데이트의 라운드별 방향·노름으로 확인해야 한다. 두 벡터의 평균을 빼서 무조건 반대 방향을 만드는 수정은 해결책이 아니다.

## 2. oracle도 실제 적용됐지만 최종 방어 효과가 없었다

oracle은 알려진 클라이언트 0·타깃 0의 최근 헤드 업데이트로 만든 **rank 1 방향**이다. 진짜 백도어 부분공간이나 완벽한 정화기를 의미하지 않는다.

- 40라운드 중 39라운드에서 양의 정화량을 적용했다.
- guard 거절은 1회뿐이다. guard가 전체 정화를 취소한 문제가 아니다.
- 시도한 정화 강도 lambda는 매번 0.5였다. 이 실행에서는 노름 예산 때문에 lambda가 추가로 줄어든 것이 아니다.
- ASR은 FU 5라운드 75.3556%, 10라운드 97.7111%, 35/40라운드 100%다.
- oracle 모델 해시는 none과 다르다. 단순히 같은 체크포인트를 잘못 읽은 것으로 설명되지 않는다.

현재 구현은 최종 학습 시점의 헤드 후보 방향을 고정하고, 초기 모델부터 재생하는 FU 과정의 해당 헤드 성분 일부를 뺀다. feature extractor와 다른 클래스 행의 공격 관련 변화는 직접 제거하지 않는다. 어느 요소가 실패에 결정적인지는 현재 로그만으로 분리할 수 없다. 탐지를 고치는 것만으로 충분하다는 근거도 없다.

## 3. 공격 잠복 조건부터 점검해야 한다

삭제 전 ASR이 5라운드 6.5889%에서 40라운드 69.7667%로 증가했다. 삭제 후 상승은 존재하지만, 낮은 ASR로 잠복한 상태에서 삭제만으로 활성화되는 강한 재현 결과로 볼 수는 없다.

`retrain`도 클라이언트 0의 백도어 데이터를 유지하고 학습한다. 삭제하는 것은 위장 클라이언트 5이므로 retrain ASR 99.9667%는 곧바로 재학습 코드 오류를 뜻하지 않는다. 잔존 데이터 자체에 백도어 학습 신호가 남아 있는 조건이다.

`clean` 후속 FL은 오염 샘플을 정상 원본으로 교체하지만 10라운드 내내 ASR 100%였다. 이 한 실행은 “정상 FL을 이어가면 자동 감소한다”는 기대를 뒷받침하지 않는다. 아직 ASR을 10–15%까지 낮추지 못했으므로, 그 수준에서 시작하는 후속 FL 가설을 검증한 것은 아니다.

## 코드에서 확인한 점과 남은 한계

- ASR은 트리거 테스트 입력에 대한 `argmax == target`의 샘플 비율이다. 모든 테스트 라벨이 target이라고 자동으로 100%를 만드는 식이 아니다.
- 원래 타깃 클래스인 이미지는 `RecordImages(..., target=...)`에서 제외한다. 라벨 순서는 원본 데이터 컨테이너의 assigned/original 순서와 일치한다.
- 매 평가 전에 전달된 모델 state를 로드한다. 로컬 학습 상태는 CPU clone으로 반환해 이전 클라이언트 결과의 참조가 덮어써지지 않는다.
- FU와 retrain은 요청자 5를 제외한다. 정화 부호는 후보 성분을 빼는 방향이며 층별 보정 이후 각 클라이언트 기여 합도 검증한다.
- 업로드 커밋의 `bd_test_dataset` 경로 보호는 유지했다. 테스트 이미지가 없을 때 같은 ID의 학습 이미지로 대체되지 않는 회귀 검증을 추가했다.
- 원본 이미지와 모델은 공유 ZIP에 없다. 실제 위장 파일의 내용, 각 테스트 예측, 원본 생성 과정까지 확인했다고 주장하지 않는다. 기존 ZIP에는 ASR 분자·분모와 logit margin도 없어 이를 사후 생성하지 않았다.
- 현재 경로 해석기는 위장 이미지의 여러 저장 위치를 허용한다. `prepare_data.sh`에도 pert 파일을 지우고 이미지를 옮기는 단계가 있으므로, 폴더 이름이나 파일 존재만으로 최적화된 위장 데이터임을 입증할 수 없다. 원 실행의 실제 파일과 전처리 기록을 대조해야 한다.

## 이번 변경과 다음 확인

방어 임계값·공격 조건·정화 강도는 변경하지 않았다. 성능 수정본으로 해석하지 않는다.

1. `audit.py` 추가: 기존 결과 폴더/ZIP에서 탐지 누락, 모델 해시 일치, 실제 정화 적용, oracle 실패, 학습 전후 ASR을 추출한다. 모델 재학습이나 FU를 수행하지 않는다.
2. 평가 출력에 ASR 성공 수/전체 수, clean/trigger 예측 히스토그램, 타깃 확률·margin을 추가했다. 앞으로 100% 포화 상태에서도 예측 강도 변화를 구분할 수 있다. 이 수치는 탐지나 정화 결정에 전달하지 않는다.
3. ASR 라벨 혼동·분모 계산·테스트 경로·업로드된 실패 결과 해석을 검증하는 테스트를 추가했다.

먼저 GPU 실행 장비에 남은 결과와 history를 아래 명령으로 확인한다. CPU에서 실행해도 되는 **저장 기록 분석**이며 실제 GPU 학습을 대체하는 실험이 아니다.

```bash
python -m experiments.request_purify.audit --input artifacts/badfu_gpu_v1 \
  --history artifacts/badfu_gpu_v1/eval-attack-42/history.pt \
  --out artifacts/badfu_gpu_v1/audit_with_history.json
```

그 다음 위장 데이터 원본·라벨·경로를 확인하고, raw 방향 신호의 실패 원인을 분석한다. 정화는 탐지와 분리하여 후보 공간·적용 위치의 효과를 비교해야 한다. 이번 seed 42를 보고 설정을 바꾸면 개발 실험이며, 최종 평가에는 별도의 seed/조건이 필요하다. **현재 결과로 탐지 성공이나 정화 가능성이 확인됐다고 주장하면 안 된다.**
